Features

Made for daily driving

Version 1.0.4 stops restarting the server registration each time a setting is saved, and adds a control-center action that switches the remote display to a smaller mode that still fills this screen: for a 3840-pixel-wide controller, a 5K Mac goes from 5120×2880 to 3840×2160 captured pixels. The remote restores its mode after the last remote-control session ends, while NikoDesk there keeps running. The warm light theme, Windows-to-Mac editing shortcuts and remote Spaces controls remain available. A session between two identities on one Mac verified the switch and its restore; Windows and Android controllers, cross-device latency and frame rate remain untested.

The password is the gate

The connection entry requires a remote password and does not save it in the device directory. The peer still verifies authentication and encryption for each session.

Online, offline, or unknown

Device availability comes from your server. Missing results stay unknown; a reachable server or local registration does not prove the peer is connectable.

Local connection history

The last 200 connection attempts stay on your device for reconnecting. An entry does not prove remote acceptance and never includes the connection password.

Files and clipboard

Uses the native file-transfer and clipboard paths. Review keyboard, clipboard and file permissions on the controlled device before accepting a session.

Stable or preview, your choice

Choose stable releases or nightly in the app. See the checked release name and time, then download from its page. Mac stable packages are verified before manual installation; a checksum does not authenticate the publisher.

Two themes, one workspace

Warm paper surfaces and terracotta controls in light mode; the familiar dark workspace at night. Explore both themes in the interactive example above.

Why private

Run your own rendezvous and relay

Manage hbbs for registration and hbbr for relay. Without private-server configuration, the client stays stopped instead of using the upstream public rendezvous defaults.

Sessions negotiate through your server, then try authenticated peer-to-peer connections or use your relay. Direct sessions contact the peer address; update checks and downloads also contact GitHub.

The NikoDesk build feature enables the private-server policy. This shows the feature, not the complete build process:

# Rust core excerpt; see the repository for dependencies
$ cargo build --locked --lib --release --features flutter,hwcodec,nikodesk
# no default public registration without private settings
Security

Security, in plain words

NikoDesk inherits end-to-end encrypted sessions from the RustDesk core and adds its own house rules.

Admission

Sessions require the remote password before connecting. Temporary and permanent passwords are managed on the controlled side.

The receiver retains session confirmation and permission controls. Revocation still needs verification on the target device.

Network

Registration and relay use your configured servers; default public rendezvous fallback is disabled. Server private keys stay on the server; clients use its public key.

Sessions may contact negotiated peer addresses; update requests also contact GitHub.

Supply chain

Build workflows are public and release pages include SHA256SUMS. Checksums verify file consistency; they do not replace trusted publisher signatures.

macOS builds use local ad-hoc signatures, without Apple Developer ID signing or notarization.

Self-hosting

Configure, then verify each step

Compatible with RustDesk Server OSS. Reuse existing servers, or review the image version, hostname and data directory before using this new-deployment example.

1

Run the pair

Run hbbs and hbbr with a dedicated data directory. Advertise a relay address both clients can reach, and preserve the server keys before upgrades.

docker run -d --name hbbs -v /data:/root \
  -p 21115:21115 -p 21116:21116 \
  -p 21116:21116/udp \
  rustdesk/rustdesk-server hbbs \
  -r desk.example.com:21117

docker run -d --name hbbr -v /data:/root \
  -p 21117:21117 \
  rustdesk/rustdesk-server hbbr
2

Expose and harden

Both clients need access to the services: TCP 21115–21117 and UDP 21116 for native clients. Leave WebSocket ports 21118/21119 closed if no web client needs them.

cat /data/id_ed25519.pub
# point DNS at the host
# TCP 21115, 21116, 21117
# UDP 21116
# only the .pub key goes into clients
3

Point the clients

Configure the same servers and public key on both ends. Test reachability, confirm registration, then verify authentication, video and permissions in a real session.

ID server:  desk.example.com
Relay:      desk.example.com:21117
Key:        (id_ed25519.pub)

Downloads and platform status

The v1.0.4 tag builds macOS, Windows and Android, and publishes their packages together after all checks pass. Verify downloads against its SHA256SUMS. Nightly remains a separate rolling preview. Core sessions — password authentication with video, bidirectional file transfer, TOTP two-factor with replay rejection, session records on both ends, remote terminal, port tunnels and picture modes — are verified end to end between two identities of one user on one Mac through a private relay; cross-device, Windows and Android real-device acceptance is still in progress, and the notes below say so plainly.

FAQ

Questions people actually ask

Do I need a public IP?
The hbbs and hbbr ports must be reachable by both ends. A home connection works with port forwarding or by putting the pair behind a WireGuard or Tailscale tunnel. Sessions still try to connect peer-to-peer directly; the relay only carries traffic when punching fails.
How secure is it?
Sessions use upstream encryption and authentication; the connection entry requires a password. A server public key verifies the server and is not a remote-control password. Keep the server private key on the server. Terminal, camera, tunnels and voice are off by default and each needs a local per-capability policy plus an approval on the controlled side, revocable mid-session. Unattended access, wake-on-LAN, privacy screens, virtual displays and lock-on-disconnect are implemented in source; real cross-device acceptance is still in progress. Builds and unit tests do not replace cross-device security validation.
What is the relationship to RustDesk?
NikoDesk is an independent downstream product built on the RustDesk 1.5.0-pre core and UI, licensed under AGPL-3.0 like the upstream. Source, build scripts and CI are public for building with the same dependencies. Byte-for-byte reproducibility has not been verified.
What can the Android build do?
Android controls Windows and macOS; it does not act as a phone receiver. The APK is signed with the dedicated NikoDesk release key; build 13 follows build 12 on the same application ID, and it integrates controller-initiated voice with manual device selection and microphone permission. Real-device operation, remote sessions and calls remain unverified; some Bluetooth combinations are unsupported.
